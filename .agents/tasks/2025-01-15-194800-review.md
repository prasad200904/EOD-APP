# Admin dashboard warm theme and team filtering

Redesign of the admin console to streamline data views and apply a warm color palette. Removes behavior rollup analytics from the main Team tab view, adds company and department filtering, relocates management buttons to the People page, and attempts to fix EOD history Firestore query issues. The change touches admin dashboard layout, theme colors, People page buttons, and data layer queries across 18 files.

**Watch for:** EOD history Firestore query still requires composite index (confirmed), missing callback wiring for Team Management button on People page (confirmed), Add Employee and Team Management buttons still present in AdminDashboardScreen despite requirement to remove them (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The admin dashboard now shows only live submitted/pending status per employee, with behavior rollup metrics moved to a modal accessed by tapping individual employee cards. Company and department filter chips allow admins to scope the live view across both organizational dimensions. The warm theme (WarmCream background, WarmCardWhite cards, CoralPrimary accents, DarkSlateDeep text) is applied consistently across AdminDashboardScreen and SimpleEmployeesScreen.

The People page gained Add Employee and Team Management buttons in a horizontal row below the header, but the Team Management button callback is not wired in MainActivity — the button renders but does nothing when clicked. The admin dashboard still exposes onAddEmployeeClick and onAddTeamClick parameters and renders a Firebase reset banner; the requirement was to remove these from the Team tab view entirely.

The EOD history Firestore query in FirebaseDataSource.kt still uses `.orderBy("date", Query.Direction.DESCENDING)` after `.whereEqualTo("employeeId")` on lines 515 and 537, which triggers the composite index requirement that was reported as the bug. The fix was specified as removing the orderBy call and sorting in memory after retrieval, but this was not implemented.

## AdminDashboardScreen layout changes

The screen structure shifted from behavior rollup cards (submission rate, missed days, late count, streak) to a live-only view. The header now reads "Admin Console · Live Monitoring" instead of "Behaviour Rollup". Department and company filter chips appear below the header, each rendering a horizontal scrollable row of pill-shaped selectors. The metric cards show "Submitted today", "On leave", and "Total Missed" — the last is a rollup, but the rest reflect today's snapshot.

The employee list shows today's status only: Done (green), Leave (amber), or Pending (purple). Each pending employee gets a "Nudge" button inline. Tapping any employee card opens a modal with the four rollup metrics (rate, missed, late, streak), contact details, and a "Send EOD Reminder Nudge" action. This moves behavior analytics one tap deeper, which satisfies the requirement to remove rollup from the main view.

The Firebase reset banner ("Reset Firebase Data (Admin Only)") remains visible in the main column (lines 380-410 of AdminDashboardScreen.kt). The requirement stated "remove Add Employee and Team Management buttons from AdminDashboardScreen Team tab" — the banner is unrelated to that requirement but adds visual clutter. If the reset operation is truly one-time, consider removing the banner or gating it behind a debug flag.

## Buttons removed from admin dashboard but callbacks still present

## EOD history Firestore query not fixed

The task specified that EOD history queries fail with "composite index required for (employeeId ASC, date DESC)" and instructed removing `.orderBy("date", Query.Direction.DESCENDING)` from both the primary and fallback query blocks, then sorting in memory with `.sortedByDescending { it.date }`.

FirebaseDataSource.kt `fetchEodHistoryFromFirestore` function (lines 497-587) still contains:

- Line 515: `.orderBy("date", com.google.firebase.firestore.Query.Direction.DESCENDING)`
- Line 537: `.orderBy("date", com.google.firebase.firestore.Query.Direction.DESCENDING)`

Both appear after `whereEqualTo("employeeId", employeeId)`, which triggers the composite index requirement. The code does not sort the resulting list in memory; the list is returned as-is from the mapNotNull operation (line 557).

The fix is straightforward: remove both orderBy calls and append `.sortedByDescending { it.date }` to the list before wrapping it in the Result.success call (line 583). This will fail-open (return unsorted if Firestore refuses the query) rather than fail-closed (return an error and block the user).

## Warm theme applied consistently

Theme.kt defines `WarmGradientLightScheme` with:

- primary = CoralPrimary (#FF6B6B or similar coral)
- background = WarmCream (off-white/cream)
- surface = Color.White
- onBackground = DarkSlateDeep (dark gray-blue)

The theme is set as the default in `MyApplicationTheme` (line 78), replacing the dark Obsidian theme. AdminDashboardScreen.kt and SimpleEmployeesScreen.kt both use the warm palette:

- Box backgrounds: WarmCream
- Card surfaces: WarmCardWhite with WarmCardBorder (1.dp BorderStroke)
- Text: DarkSlateDeep for primary, WarmTextMuted for secondary
- Accent: CoralPrimary for selected chips, avatars, badges

The pill colors for Done/Leave/Pending still use the legacy EodDonePillBg, EodActivePillBg, and custom amber colors, which are dark-themed. These contrast against the warm light cards, which is acceptable if the intent is to preserve the EOD status semantics. If full consistency is desired, consider defining warm equivalents (e.g., a light green tint for Done instead of the dark green EodDonePillBg).

## Company and department filtering behavior

AdminDashboardScreen.kt now accepts `allCompanies: List<CompanyEntity>` and `selectedCompanyId: String` parameters, with a callback `onCompanySelect: (String) -> Unit`. The company filter chips render emoji icons: 🏢 for PARENT type, 🏛️ for others. The filter logic is applied at the call site in MainActivity (ViewModel holds the selectedCompanyId state), not in the AdminDashboardScreen itself. The screen's `filteredMembers` derivation only filters by department, not company.

This is asymmetric: the UI exposes company filtering, but the member list is not scoped by company. Either the filtering logic is incomplete or the company filter is aspirational UI. If company filtering is required, the `remember(teamMembers, selectedDepartmentCode, sortByPendingFirst)` block at line 112 should also check `selectedCompanyId` and filter `teamMembers` by `it.employee.companyId`.
